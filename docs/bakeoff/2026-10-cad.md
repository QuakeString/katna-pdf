# CAD prototype: scenes for vector-heavy pages (2026-10-17)

This is the Phase 0 CAD prototype from `docs/PLAN.md` §2.5, steps 1, 2, 3
and part of 4. Page 1 is read once into a scene. Each tile then draws only
what an R-tree finds inside it.

- **Code:** `crates/katna-pdf-render/src/scene.rs`.
- **Benchmark:** `katna-pdf-bench --cad FILE…`.
- **Check against hayro:** `katna-pdf-bench --scene-check FILE…`.

## What it does

- **Detect.** A page whose own content stream builds at least 50,000 path
  segments counts as vector-heavy (`is_vector_heavy`). Other pages never
  pay for a scene.
- **Read once.** hayro-interpret reads the page into a scene. Each path's
  points go into flat arrays, colours and strokes are shared, and clips
  form a tree. Every item gets its bounding box in page points, with its
  clip applied.
- **Index.** All boxes are bulk-loaded into an `rstar` R-tree.
- **Draw a tile.** The tree is asked for the tile's box, and the items it
  finds are drawn in page order with vello_cpu. Clips are opened and
  closed only as they change. Hairlines are kept at least a pixel wide, as
  hayro draws them.
- **Level of detail.** An item smaller than ¾ pixel on both sides is
  drawn as a dot of its colour instead of being stroked or filled.
- **Fallback.** A page holding anything the scene cannot draw yet is drawn
  the usual way. That covers images, patterns and shadings, soft masks,
  blend modes, groups that change opacity, and Type 3 text.

`Hayro` uses scenes. `HayroPlain` never does; it is there so the two can be
compared.

## Speed

Each step draws a 1920 × 1080 view as 512-pixel tiles on all 4 cores of a
2.1 GHz Xeon. The steps are the sheet fitted to the view, then 100 %,
400 % and 3200 % around the sheet's middle. "Sheet" includes opening the
file and, for scenes, reading the page into the scene. Times are in ms;
**!** marks a miss of the §2.5 budget (600 ms to the first sheet, 250 ms
per zoom step).

| Sheet | Scene | View | Scene ms | Usual ms | Faster |
|---|---|---|---:|---:|---:|
| A1, 100k strokes | 100k items, 12 MB | sheet | 262 | 483 | 1.8× |
| | | 100 % | 73 | 612 ! | 8× |
| | | 400 % | 9 | 477 ! | 55× |
| | | 3200 % | 2 | 431 ! | 232× |
| A0, 400k strokes | 400k items, 47 MB | sheet | 846 ! | 2,105 ! | 2.5× |
| | | 100 % | 92 | 1,811 ! | 20× |
| | | 400 % | 14 | 1,836 ! | 129× |
| | | 3200 % | 3 | 1,872 ! | 548× |
| A0, 1M strokes | 1M items, 99 MB | sheet | 2,142 ! | 4,785 ! | 2.2× |
| | | 100 % | 274 ! | 4,458 ! | 16× |
| | | 400 % | 33 | 4,016 ! | 122× |
| | | 3200 % | 4 | 4,148 ! | 955× |

The sheets come from `bakeoff/make_cad.py`.

For comparison, the engine bake-off (`docs/bakeoff/2026-10-engines.md`)
measured the 1M sheet differently, as one page at 150 % and one 1024²
tile at 800 %:

| Engine | Page at 150 % (ms) | 1024² tile at 800 % (ms) |
|---|---:|---:|
| PDFium | 12,444 | 1,492 |
| MuPDF | 21,170 | 5,262 |

A scene draws a whole 1920 × 1080 view at 400 % in 33 ms. Okular was not
measured, because it cannot be installed on the build machine.

What the numbers say:

- **Zooming in now costs what is on screen, not what is on the page.** At
  400 % and deeper, every sheet is far within the 250 ms budget, and
  deeper zoom is faster, as §2.5 intended.
- **The first full-sheet view of the largest sheets still misses.** On the
  1M sheet it takes about 1.2 s to read the page and 0.95 s to draw every
  stroke. Every stroke is larger than a pixel at that zoom, so the dots do
  not help. That leaves two steps of §2.5 to do:
  - Precomputed overview levels, where strokes merge into tone.
  - Showing a quick hayro preview at screen size while the scene builds.
- **Memory** is about 100 bytes an item: 99 MB for 1M strokes, inside the
  300 MB budget.
- **Batching** strokes of the same style into one path was tried and
  dropped. It was no faster, and anti-aliasing changed where strokes
  overlap.

## Correctness

`--scene-check` draws page 1 of each of the 994 files in the pdf.js test
corpus at 150 %, from a scene and the usual way, then compares the two.
This covers every page a scene can draw, vector-heavy or not.

- **Drawn from a scene:** 631 pages. Only one differs in more than 0.05 %
  of its pixels: `issue16316.pdf`, at 0.08 %.
- **Fallback:** 342 pages hold something a scene does not draw yet: 203
  images, 59 patterns, 27 groups, 24 Type 3 fonts, 16 blend modes and 13
  soft masks.
- **No page opened:** 19 files.
- **Timed out:** 2 files, `bomb_giant.pdf` and `bug1978317.pdf`. Both are
  just as slow when drawn the usual way.

Two bugs the check found are fixed:

- Text strokes were drawn too thin, because they went through the font
  matrix.
- Empty glyphs and zero-length butt-capped dashes showed up as dots.

## Not done yet

- **Real AutoCAD exports.** The one real plan in the corpus,
  `22060_A1_01_Plans.pdf`, draws its drawing through tiling patterns that
  hold images, so it falls back to the usual path. Real exports are needed
  to tune the detector and the fallbacks.
- **Images and patterns in scenes.** Title blocks and logos often carry
  them. Supporting them would keep such drawings on the fast path.
- **Form XObjects.** The detector does not count segments inside them yet.
- **The rest of §2.5:**
  - Overview levels.
  - The tile pyramid with the nearest ready level shown scaled.
  - Fast, unsmoothed drawing while a zoom is in motion.
  - Layers.
